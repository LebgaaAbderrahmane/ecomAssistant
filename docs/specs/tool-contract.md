# Spec: one tool contract

- **Status:** proposed
- **Related:** `docs/REWORK_PLAN.md` Phase 2, `docs/grpc-contract.md`, issue #80

## 1. Problem

Tool metadata exists in three places that drift independently:

1. `contracts/src/generated/tools.json` — generated by `back/scripts/export-contract.ts`, committed.
2. `back/src/modules/ai/schemas/intents.schemas.ts` + `tools/toolMeta.ts` — the source zod schemas and descriptions.
3. `ecom_agent/tools/__init__.py` + `tools/registry.py` — hand-copied names, descriptions, and Python argument schemas.

The gRPC messages still carry JSON strings:

- `ExecuteToolRequest.entities_json`
- `ExecuteToolResponse.data_json`
- `GetConversationContextResponse` JSON fields

So we pay the full cost of protobuf (proto files, codegen, two servers, shared-secret auth, a contract doc) and still parse untyped JSON at both ends. Python has no test that its view of a tool matches the generated catalog.

## 2. Goal

One source of truth for tools, one generated artifact, typed payloads, and a CI parity check that fails on drift.

## 3. Source of truth

`back` remains the source: zod schemas + tool metadata. The generated artifact stays `contracts/src/generated/tools.json`, extended with what the agent needs:

```json
{
  "version": 2,
  "tools": [
    {
      "name": "createOrder",
      "description": "...",
      "args": [
        { "name": "productId", "type": "string", "required": true, "description": "..." },
        { "name": "quantity", "type": "integer", "required": true, "minimum": 1, "description": "..." }
      ],
      "ask": {
        "productId": { "fr": "Quel produit ?", "ar": "...", "derdja": "..." },
        "quantity": { "fr": "Combien ?", "ar": "...", "derdja": "..." }
      },
      "writes": true,
      "idempotent": true
    }
  ]
}
```

Rules:

- `ask` templates live with the tool so the deterministic question step has no hardcoded strings.
- `writes` and `idempotent` let the turn module decide retry policy without a name list.
- The file is generated, committed, and checked by CI. Nobody edits it by hand.

## 4. Codegen

Two generators from the same JSON:

- **Python:** `contracts/scripts/gen_python.py` writes `ecom_agent/tools/generated.py` with typed dataclasses (or `TypedDict` + validators) and the descriptions.
- **TypeScript:** the existing export script keeps producing the JSON; `back` already imports `TOOL_NAMES` from `contracts`.

CI check:

```
pnpm --filter @ecomassistant/back export:contract
git diff --exit-code contracts/src/generated/tools.json
python contracts/scripts/gen_python.py --check
```

Any schema or description change that is not regenerated fails the build.

## 5. Tool cut: 11 → 7

| Tool | Status | Notes |
|---|---|---|
| `searchProducts` | keep | exact match returns full details, so `getProductDetails` is redundant |
| `getOrderStatus` | keep | status + tracking |
| `quoteOrder` | new (renamed from `calculateShipping`) | returns product total, delivery, grand total for a candidate order |
| `createOrder` | keep | idempotency key required |
| `confirmOrder` | keep | state guard required (see issue #45) |
| `cancelOrder` | keep | state guard required |
| `escalateConversation` | keep | sets takeover, writes reason |
| `selectProduct` | remove | session field set by the merge step |
| `getProductDetails` | remove | covered by `searchProducts` |
| `suggestProducts` | remove | prompt behavior over `searchProducts`; drops the Gemini call inside `back` |
| `calculateShipping` | remove | folded into `quoteOrder` |
| `modifyOrder` | remove for now | reintroduce only with usage data; until then cancel + recreate or escalate |

Removal is a contract change. `back` keeps the implementations until the agent no longer calls them, then deletes the schemas, metadata, and `LEGACY_ONLY_TOOL_NAMES`.

## 6. Typed gRPC payloads

Replace JSON strings with `google.protobuf.Struct` **only if** the team accepts the validation cost. Preferred: explicit messages per tool.

```proto
message ExecuteToolRequest {
  string tool_name = 1;
  ToolIdentity identity = 2;
  string idempotency_key = 3;
  oneof args {
    SearchProductsArgs search_products = 10;
    GetOrderStatusArgs get_order_status = 11;
    QuoteOrderArgs quote_order = 12;
    CreateOrderArgs create_order = 13;
    ConfirmOrderArgs confirm_order = 14;
    CancelOrderArgs cancel_order = 15;
    EscalateConversationArgs escalate_conversation = 16;
  }
}

message ExecuteToolResponse {
  bool success = 1;
  string outcome = 2;
  oneof result {
    SearchProductsResult search_products = 10;
    OrderResult order = 11;
    QuoteResult quote = 12;
    ErrorResult error = 13;
  }
}
```

Rules:

- `identity` is always server-derived on the `back` side; the agent sends ids it received from `back`, never values it invented.
- Every RPC has a deadline (default 8s, tool-specific override).
- Errors use a typed `ErrorResult` with `code`, `message`, `retryable`; no exceptions across the boundary.
- Unknown `oneof` variant → `INVALID_ARGUMENT`, not a crash.

If full typing slips, the fallback is: keep `Struct`, validate with generated JSON Schema on both sides, and add the parity test. Do not keep hand-written Python schemas as the only check.

## 7. Acceptance criteria

- [ ] `contracts/src/generated/tools.json` is the only catalog; Python imports generated types, no hand-copied tool list or descriptions.
- [ ] CI fails if the catalog is stale or Python generated code differs.
- [ ] Exactly 7 tools registered; removed tools have no schema, metadata, or routing branch.
- [ ] `suggestProducts` no longer calls an LLM inside `back`.
- [ ] gRPC requests/responses are typed messages (or validated `Struct` with generated JSON Schema); no unvalidated `entities_json` / `data_json`.
- [ ] Every RPC has a deadline and returns typed errors; no exception crosses the boundary.
- [ ] Contract test covers: name parity, arg parity (name/type/required), description parity, and unknown-tool rejection.
- [ ] `docs/grpc-contract.md` is regenerated from the proto, not hand-edited.
